**Built**
- **Mediathèque in Assets** (`src/assets/mediatheque.js`, `src/ui/MediathequePanel.js`): the public archive `languel.github.io/mediatheque` (repo `~/dev/mediatheque`) as a second view with **My assets | Mediathèque** tabs, shown only while the catalog loads. Items are added as references (a stream asset `mediatheque:<id>`, credit and rights kept) or copies; ⌘/Ctrl-click picks several; **▶ Timeline** on every card. GIF items use their `video_media` (mp4). Base can be a local checkout: `localStorage.ams_mediatheque_base`.
- **Media clips** (`src/workbench/mediaClips.js`): a `media` track on the take; clips are references `{ url, asset, in, out, speed, fit, opacity, volume, credit }`, stills are 5 s clips, boards can be clips (`board`). Player: `TakePlayer.syncMedia/drawMedia`. A take with only media/titles/sound is *composing*: the canvas stays live (no view-only hand).
- **NLE basics** in `panels/timeline.js`: append at the playhead (a clip added over another goes after it), **X** splits (a shortcut in `shortcuts.js`), **⇧⌫** ripple delete.
- **Program board** (`src/workbench/timelineSource.js`, `app.ensureProgramBoard`): the first media clip makes a 16:9 board whose source is `timeline`: the take at the playhead. It is the sequence's monitor and what outputs (pin, window) take from.
- **Export a clip** as MP4/WebM/GIF with **ffmpeg.wasm** (`src/media/ffmpegRunner.js`, single-thread core, lazy, ~30 MB, 250 MB source limit): board menu › Clip, Assets preview, media clip Properties.
- **Keyframe dot, spike to first version** (`src/process/keyframes.js`, `src/workbench/params.js`, `src/workbench/keyframeDot.js`): one lane type (`auto` clip: `{address, keys:[{t,v,ease}]}`, keys relative to the lane), addresses `board:`, `mark:`, `ctl:` (sketch controls, set live without touching the code), a diamond beside any field made with `numberField({ address })` and every sketch control, a row per lane on the Timeline with its key diamonds (square-ended bars, keys exactly on their time). Numbers ease; `#rrggbb` colours and palettes blend; choices step through their options and snap to the nearest; toggles snap half-way (`mix` in `keyframes.js`, lane `meta.options`). **State tint**: the field (or a sketch control's row) is green when a lane drives it, yellow with a key at the playhead, orange when changed since (`kf-anim/kf-key/kf-dirty`); the diamond keys it. **Auto-key** (Timeline bar button, localStorage `ams_autokey`, off by default) keys a changed animated parameter at the playhead; `userChanged()` handles sketch sliders (sets the running value, the code keeps its default); the player's `applying` flag stops lane-set values from counting as changes.
- **Plan** [camera-plan.md](camera-plan.md): several cameras, parallax, one keyframe system, a deterministic frame-by-frame render (decisions in its section 0).

**How the new parts fit**
- The Timeline is per scene (the take is remembered by the scene; transport settings are the scene's).
- `app.player.applyAutomation()` runs on every `render()`; `seek()` clears the applied cache; `BoardFrames.automated` stops the code-to-sketch value sync from overwriting a control a lane drives (any new code that pushes values from a source of truth needs the same rule).
- Automation writes values into the document with `transient: true` (no undo step) and they stay in the saved scene.
- Dev server note: after a code edit the page reloads and an unsaved take is lost; test in one go.

58. **Time envelopes** (`process/envelope.js`): a mark can carry `time: { in, hold, out, life, draw, curve, loop }` (seconds) and `born` (epoch ms). `renderDocument(…, { now })` fades it by its age, draws its stroke on (`cutPath`), drops it after its life; `timedActive` keeps the canvas redrawing until nothing changes. Brushes read `k.age`. Callers that want a still of a live picture pass `now: Date.now()` (snapshot, bake, board sources do); the p5 exports and takes do not yet.
59. **Textured brushes** (`process/texture.js`, embedded in exports): a mark is painted white into a cached layer (world units, `ppu` in half-octave steps, cap 2048 px, 96 MB LRU), the paper's grain (`paper | canvas | fibre | noise`, anchored to the world) is multiplied in, and it is tinted. Kit: `k.paint / dabs / hairs / wash / bounds / hash / grain`. Brushes: charcoal, chalk, pencil, bristles, **oil** (packed hairs, streaks, taper, ragged ends), marker, wash. The layer cache survives a lost canvas context (`txReady`: nothing is painted while contexts are lost, then everything kept is dropped) and gives evicted canvases back; the canvas view repaints on `contextrestored`. We saw the browser pane lose every canvas at once after ~40 s of heavy painting.
60. **Painterly, fading strokes** (board menu → Draw from a source; `sourceDemos.js`, id `paint`): plain board code, after Hertzmann. Four layers, each seeing the source blurred as much as its brush is broad (`s.pixels(64, …)` on a grid); a coarse model of the live strokes (weighted by their envelope); each layer looks at blocks the size of its brush and starts a stroke at the worst place of a block that differs and that the layer has not painted itself (`own` coverage); the first layer always paints; the paper is toned to the source's mean (`memo.ground`, a plane under the strokes); `state('paint')` keeps strokes so `born` and `seed` are stable and the layer cache hits. Four earlier versions failed in instructive ways (see `exports/klee-painterly/report.html`, *How it got here*): worst-cell placement stacks strokes on the hardest zones; blocks without own coverage repaint the same blocks; without a toned paper and an always-on underpainting quality decays as strokes fade.
61. **AMS → p5.js for our brushes** (`p5code.js`): a board's code exported as a sketch carries the studio's textured brushes it names (`brushSource(id)`, flagged `texture: true`), the walk (`walk.js`: `smoothPath`, `walkFrames`, split out of `brushes.js` and embedded with it in exports, pages and takes), the layer kit (`texture.js`) and time envelopes (`envelope.js`: `fade`, `drawn`, expired marks skipped), each in an IIFE so the sketch's globals stay clean; `useBrush` seeds a rng per mark. A still picture's pixels are read once and an empty read is not kept (a browser can drop canvases; the sketch then painted every stroke black). Round trip to studio code unchanged. Sample: `exports/klee-painterly/p5-sketch/`. Live, the p5 boards match the AMS ones in look and in number.
62. **The Klee experiment and report:** `experiments/klee-painterly/` (harness: simulated clock and seeded random, snapshots and metrics: error, SSIM, covered; `receiver.py` saves to `exports/klee-painterly/`, which is git-ignored) and `scripts/klee-painterly-report.mjs` (builds the report as a drawing with boards, `report.html` and a document the studio opens as a scene). Findings: stable for 60 s; about a 24×24 mosaic in fidelity; chalk and bristles beat oil and charcoal on faithfulness; tolerance barely matters; a fifth layer +0.06 SSIM for double the marks. Scenes in the pane: *Klee · AMS (painterly, only AMS)*, *Klee · p5 (same sources, our brushes in p5)*, and the report scene.

63. **Performance of textured, timed marks** (details and numbers: `docs/notes/painterly-performance.md`; bench: `experiments/klee-painterly/bench.html`): a textured mark's layer is painted once and blitted (`txKnown` / `txBlit`, `drawTextured` in `render.js`); drawing on is a clip (`revealClip`, also in the p5 export); the cache keeps last-used stamps, sweeps layers of long-gone marks, caps a layer at 250 000 px and paints smaller (`txQuality`) when layers in use had to go; `renderDocument({ view })` skips marks outside the view; timed animation redraws at most 15 times a second and only while something moves (`nextChange`, `nextTimed`); `runScript` no longer copies its own document (`normalizeDocument(doc, { own: true })`); the demo caches the source's blurred layers by `s.frame`, keeps flat typed arrays, rebuilds its model twice a second. Frame (run + draw) 77 ms to 7.8 ms; in the app the main thread is 15% (no fades) to 25% busy with one board live, pane in front (a hidden pane is throttled). ## How the model fits

```
project (shared: Assets, brush & sculpt libraries, settings)
└─ scene = one process document (own undo, History, Timeline)
   ├─ boards: main (artboard at 0,0) + doc.boards[] {id, title, x, y, width, height, ground, text?, code?, follow?, source?}
   ├─ blackboard: marks with board '_'
   ├─ stages, marks (points [x, y, t, pressure]; pressure may exceed 1 after Thicken)
   └─ meta.intro (page intro), train (the board models learn from)
```

## LFM3-Omni as the mainstay, and the Pi coding-agent space (ideas, 5 Nov 2026)

**If LFM3-Omni (browser) is the mainstay, tune the tooling to it with controlled experiments.** Proposed, each measured on `assistEval.js` (and a bigger paraphrase set, below):
1. **Flat, typed tools instead of one generic nested one.** Liquid's demos give the model few tools with flat arguments (a timer, a theme). Ours were `ams_update {id, patch: {…}}`, where the model also has to build the nested patch. Try `ams_set_fill {id, color}`, `ams_set_opacity`, `ams_move {id, dx, dy}`, `ams_scale {id, factor}`… and re-test its native tool calling (`localStorage.ams_native_tools = '1'`), which was worse than JSON before; the tool shapes may be why.
2. **A stable system prompt, with the changing state in the user turn.** The Pi space's config says: "Keep the tool definitions and instructions stable to reuse the session's KV cache." Our flow prompt puts the marks on the page in the system prompt, so every request invalidates the cache. Moving the state into the user message should make requests faster.
3. **Block a repeated failed call with a hint** (the agent loop in that space returns "This exact call already failed: … Change the call"), instead of letting the model repeat it.
4. **Voice straight to a tool call.** Omni listens: send the recorded audio with the tools and compare it with Whisper then phrases then model.
5. **A larger paraphrase set** (3 or more per task, generated by a coder model and checked) so that differences of one or two tasks stop being noise.

**`webml-community/LFM3-1.7B-WebGPU-Pi`** ("LFM3 WebGPU Workspace"): a browser workspace (terminal, editor, a virtual file system and shell, `just-bash`, Apache-2.0; terminal parts MIT; UI Apache-2.0) where **LFM3-1.7B** (text only; `LFM3-1.7B-Q4_K_M.gguf`, about 1.1 GB; 32k context) is an agent with tools `read`, `write`, `edit` and `bash`, up to 12 rounds, greedy. The runtime (`dist/runtime/Lfm3ForCausalLM.js`, 1 MB) and the agent loop (`dist/runtime/agent.js`, 6 KB) are served by the space (no licence text for the runtime: load it at run time like the Omni one, do not copy it). What to take:
- **An LFM3-1.7B text engine** next to Omni (1.1 GB against 1.6 GB, same family): add it as a second library in `Lfm3WebGPUArtist.js` (the library URL and class name become settings) and run the chat and lesson evals on it.
- **A board-code agent** (our own, in the AMS tools): `read_board_code`, `edit_board_code` (replace this text with that), `run_board` (returns the studio's `{error, line}` or the mark count), then look again. Editing and re-running suits a small model better than rewriting a whole program, and gives students "make the dots bigger" as a conversation with the code. Instructions modelled on theirs: "Inspect before editing. Verify with a tool, then give a short factual answer."
- Not the workspace itself (its file system and terminal duplicate what the code boards and Code panel already are).

## Idea: a family of LFMs by role, orchestrated (5 Nov 2026)

Instead of one model for everything, stay in the Liquid ecosystem and give each job its own LFM, with an LFM (or an outside agent over MCP) deciding who does what. The **Code model** setting is the first step: it already says "conversation here, code there". Generalize it into **roles**, each an engine and a model (`modelFor(role)` in `modelStore.js`, the settings shown the same way):

| Role | What it does | LFM candidates (status) |
|---|---|---|
| talk / orchestrate | conversation, commands, drawing; decides which tool or role to use | LFM3-Omni 2B (browser, 15/16 with the instant phrases); LFM3-1.7B text (being tested) |
| code | writes and fixes board code | LFM3-Omni 9/14 and 7/14 (weak for code); LFM3-1.7B, LFM2.5-2.6B, LFM2.5-8B-A1B, LFM2-24B-A2B (to test); a small LFM fine-tuned on AMS code (the sub-1B idea, base `LFM2.5-230M`); Qwen coders are the benchmark (14/14) |
| see | looks at a picture, a board, a reference | LFM3-VL 2B (browser runtime works; weak at code, not tested at seeing), LFM2.5-VL 1.6B and 3B (ONNX, in the browser) |
| hear / speak | dictation, spoken replies, narration | LFM3-Omni (speech in and out, working), LFM2.5-Audio 1.5B (speech recognition and speech in transformers.js, to try) |

**Orchestration comes through the tools, so the same surface serves an inner LFM and an outside agent.** AMS already is an MCP server (`ams_*`). An inner orchestrator uses flat tools whose implementation calls a role: `ams_write_code` calls the code role; a new `ams_look {board}` would call the see role on a snapshot and return a description; speak and transcribe call the voice role. An outside agent (Claude Code, another harness) calls the same tools and so sees the same roles.

**Browser memory is the constraint.** Omni (1.6 GB) + a coder (1 to 2 GB) + a VL (1 GB) is 4 to 5 GB of weights: load a role on first use, keep the last two or three, evict the rest, and show it (the status line already shows downloads); a slow first use is the cost, so say so.

**Honest state:** for code, the Liquid models measured so far trail the Qwen coders by a wide margin (9/14 and 7/14 against 14/14). Whether an all-Liquid code role is realistic depends on the LFM3-1.7B and LFM2.5-8B-A1B results and on fine-tuning a small LFM on the lesson boards and the request log.
